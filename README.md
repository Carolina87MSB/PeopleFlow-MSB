# Portal PeopleFlow · MSB

Portal interno de RH da MSB para gestão de **movimentações de pessoal** (admissão, promoção, transferência, alteração salarial, mudança de função, desligamento e criação de cargo), com fluxo de aprovação em etapas (Gestor → RH/Diretoria → CEO, conforme o tipo), visão de dashboard, cadastros (colaboradores, departamentos, cargos), trilha de auditoria e fechamento financeiro de desligamentos (rescisão, GRRF).

Reconstruído a partir de um protótipo visual (`Portal PeopleFlow MSB.zip`, formato proprietário de prototipagem) como uma aplicação real em **React 19 + TypeScript + Vite**, com arquitetura em camadas e **Supabase** como backend — o **mesmo projeto Supabase do [Portal SST MSB](https://github.com/Carolina87MSB/Portal-SST-MSB)**, deploy na **Vercel**.

## Como rodar localmente

Pré-requisito: [Node.js](https://nodejs.org) 20+ e um projeto Supabase já configurado para o Portal SST (mesmo `.env.local` dele funciona aqui).

1. **Rode o schema deste portal**: abra _SQL Editor_ no painel do MESMO projeto Supabase usado pelo SST, cole o conteúdo de [`supabase/schema.sql`](supabase/schema.sql) e execute. Isso:
   - adiciona colunas novas à tabela `colaboradores` já existente do SST — `vinculo` (CLT/PJ/Estágio), `depto_code`, `nivel`, `gestor`, `admissao` (organograma) e `desligado`/`data_desligamento`/`motivo_desligamento`/`desligado_by` (essas últimas também gravadas pelo próprio Portal SST ao desligar alguém — ver `api/desligar-colaborador.ts` dele) — **não remove nem altera nada que o SST já usa** (a coluna antiga `matricula` continua existindo, só não é mais lida/gravada pelo app);
   - cria três tabelas exclusivas deste portal: `peopleflow_movimentacoes`, `peopleflow_cargos_custom` e `peopleflow_desligamentos` (fechamento financeiro), com RLS liberando leitura/escrita para qualquer usuário autenticado.
2. **Provisione a primeira conta (a sua, do RH)**: diferente do SST (só RH tem conta), aqui **todo Gestor, Diretor e RH que for usar o portal precisa de uma conta no Supabase Auth**. Para a primeiríssima conta (RH, que vai gerenciar as demais pela tela `/acessos` do próprio app — ver abaixo), crie manualmente em _Authentication → Users → Add user_. As contas seguintes não precisam mais do painel do Supabase.
3. **Configure o ambiente local**:
   ```bash
   cd portal-peopleflow
   cp .env.example .env.local
   # preencha com VITE_SUPABASE_URL e VITE_SUPABASE_PUBLISHABLE_KEY do MESMO projeto do SST
   npm install
   ```
4. **Popule os campos do PeopleFlow para os colaboradores reais** (opcional, mas necessário para o organograma/hierarquia funcionar corretamente — sem isso, vínculo/gestor/nível/admissão aparecem como "—" para todo mundo): crie um `src/data/colaboradores.local.json` (gitignored) no formato de [`src/data/colaboradores.example.json`](src/data/colaboradores.example.json) — só precisa de `{ nome, vinculo, deptoCode, nivel, gestor, admissao }`, o `nome` tem que bater exatamente com o `nome` já cadastrado no SST — e rode:
   ```bash
   npm run seed:supabase src/data/colaboradores.local.json
   ```
   Esse script só faz `UPDATE` (nunca `INSERT`) — colaboradores são cadastrados pelo SST, o PeopleFlow só completa os campos que faltam.
5. **Rode o app**:
   ```bash
   npm run dev      # http://localhost:5173
   npm run build    # build de produção em dist/
   npm run lint     # oxlint
   ```

## Deploy na Vercel

1. Importe o repositório na Vercel (framework detectado automaticamente: Vite).
2. Em _Settings → Environment Variables_, adicione:
   - `VITE_SUPABASE_URL` e `VITE_SUPABASE_PUBLISHABLE_KEY` — os **mesmos valores já usados no deploy do SST** (mesmo projeto Supabase). Lembre do prefixo `VITE_` (Vite, não Next.js).
   - `SUPABASE_SERVICE_ROLE_KEY` — **sem** prefixo `VITE_` (fica só no servidor, nunca chega ao navegador). Usada pelas Serverless Functions em `api/*.ts` para a tela de administração de acessos.
   - `GMAIL_USER` e `GMAIL_APP_PASSWORD` — opcionais, ativam as notificações de movimentação por e-mail (ver seção abaixo). Sem elas, o fluxo de aprovação funciona normalmente, só não envia e-mail.
3. Em Supabase → _Authentication → URL Configuration_, adicione a URL da Vercel deste projeto (diferente da URL do SST) na lista de _Redirect URLs_ permitidas — senão o link mágico do e-mail quebra em produção.

## Acesso

Login por **link mágico** (e-mail corporativo `@msbbrasil.com`, sem senha) via Supabase Auth — ver `src/auth/AuthContext.tsx`. Só entram e-mails com conta previamente criada no Supabase (`shouldCreateUser: false`); não há cadastro aberto. Depois de autenticado, o app cruza o e-mail com a tabela `colaboradores` (`buildAccess()` em `src/domain/hierarquia.ts`) para descobrir nome/cargo/perfil — se o e-mail não corresponder a NENHUM colaborador cadastrado (nome diferente do que o app deriva o e-mail), a tela mostra um aviso pedindo para falar com o RH (ver `AppShell.tsx`).

Três perfis, com visão e permissões diferentes (ver `src/domain/permissoes.ts`):
- **RH** — acesso completo: todos os colaboradores, todas as movimentações, cadastros de departamentos/cargos, e a tela de **Acessos** (`/acessos`).
- **Gestor** — pode solicitar movimentações e aprovar a etapa "Gestor Solicitante" para toda sua equipe (hierarquia direta e indireta, via `descendants()` — esse escopo mais amplo vale para `movimentacoesVisiveis`). O seletor de colaborador em "Nova movimentação", porém, **não é restrito à hierarquia** — mostra todos os colaboradores ativos da empresa (`colaboradoresParaSelecao` em `NovaMovimentacaoModal.tsx`), já que um gestor pode precisar abrir uma solicitação para alguém fora da própria equipe. Na tela **Colaboradores** (`/colaboradores`), o escopo volta a ser mais estrito: só vê quem tem ele como **gestor imediato** (reporte direto, sem descer mais níveis) — e sem os botões de edição (Admissão, descrição de cargo), exclusivos do RH.
- **Diretoria** — vê a mesma base de colaboradores que o RH em `/colaboradores` (sem escopo), mas sem nenhum botão de edição — RH é quem edita. Nas movimentações, continua vendo só o que ela mesma solicitou ou precisa aprovar.

`colaboradoresListagem` (fonte de `/colaboradores`, com a regra por perfil acima) é diferente de `colaboradoresVisiveis` (escopo de hierarquia completa do Gestor, usado no resto do app) — ver `usePortalData.ts`.

### Exceção de aprovação para o CEO

Daniel (CEO) e Yuri (Diretor Industrial) têm o mesmo perfil "Diretoria", mas **só o CEO** tem uma regra especial: toda movimentação que ele solicitar pula as etapas "Gestor Solicitante" e "Diretor Industrial" e vai direto para o RH — em qualquer tipo de movimentação. Yuri, com o mesmo perfil, continua seguindo a matriz normal.

A checagem é por **cargo** (`ehCEO()` em `src/domain/hierarquia.ts`, "CEO" como palavra isolada em qualquer posição do cargo — o cargo real do Daniel é "Diretor Geral - CEO", não só "CEO"), não por perfil nem por nome fixo — se um dia outra pessoa assumir o cargo de CEO, a regra passa a valer para ela automaticamente, sem precisar mexer no código. Implementado em `montarEtapas()` (`src/domain/workflow.ts`), que agora recebe quem está solicitando para decidir a matriz de etapas.

**Bug corrigido em 2026-07-30**: a regex original exigia que o cargo *começasse* com "CEO" (`/^ceo\b/`), o que nunca bateu com "Diretor Geral - CEO" — `ehCEO()` retornava `false` para o Daniel, e a etapa "Diretor Industrial" não era pulada. Isso já tinha exigido um patch manual numa movimentação real (`supabase/corrigir_fluxo_m2026_004.local.sql`, admissão de Emanoela) antes de a causa raiz ser encontrada. Trocado para `/\bceo\b/` (agora casa "CEO" em qualquer posição do cargo, não só no início).

### Visão total do Workflow e de Aprovadas para o Diretor Industrial

Mesma ideia da exceção do CEO, mas do outro lado: **só o Yuri** (cargo "Diretor Industrial") vê todas as movimentações em `/workflow` e `/aprovadas`, não só as que precisa aprovar ou que ele mesmo solicitou (regra normal de "Diretoria", que Daniel/CEO continua seguindo). Somente leitura — não muda `podeAgir()`, então os botões Aprovar/Reprovar continuam aparecendo só nas etapas que já eram dele.

Checagem por **cargo** (`ehDiretorIndustrial()` em `src/domain/hierarquia.ts`, mesmo padrão de `ehCEO()`), passada como um parâmetro extra em `canSeeMov()` (`src/domain/permissoes.ts`).

Cargos de liderança passaram a usar o marcador de gênero neutro "(a)" (ex.: "Diretor (a) Geral - CEO", "Diretor (a) Industrial") — `CARGO_DIRETOR_INDUSTRIAL` (e a mesma lógica em `CARGO_CEO`) tolera "(a)" no meio do texto (`/^diretor\s*(\(a\))?\s*industrial\b/`), senão um `^diretor industrial\b` estrito quebraria assim que o cargo do Yuri fosse renomeado.

### Tela de administração de acessos (`/acessos`, RH-only)

Depois que a primeira conta do RH estiver provisionada manualmente (passo 2 acima), o próprio RH consegue liberar o acesso de qualquer Gestor/Diretor direto pelo app, sem entrar no painel do Supabase: a tela lista todo colaborador cadastrado com o e-mail derivado do nome e um status "Provisionado"/"Sem acesso", com um botão "Liberar acesso" por linha.

Isso funciona via duas Vercel Serverless Functions (`api/listar-acessos.ts`, `api/provisionar-acesso.ts`) que rodam só no servidor: confirmam que quem chamou é RH autenticado e então usam a `SUPABASE_SERVICE_ROLE_KEY` para criar a conta no Supabase Auth — essa chave nunca é enviada ao navegador. **Essas duas functions só funcionam em produção (Vercel) ou com `vercel dev`** — `npm run dev` (Vite puro) não executa `/api/*`, então localmente a tela mostra erro de carregamento; isso é esperado.

### Editar admissão (`/colaboradores`, RH-only)

Na ficha do colaborador, o campo "Admissão" tem um botão de editar (ícone de lápis) visível só para RH — os demais campos (Cargo, Departamento, Vínculo, Nível, Gestor imediato) continuam somente leitura, pois hoje são cadastrados via `npm run seed:supabase` (ou pelo SST, no caso de Cargo/Departamento), não pela tela.

### Tipos de movimentação suportados

Só 5 tipos existem hoje: **Admissão, Promoção, Alteração Salarial, Transferência, Desligamento** (`src/data/tiposMovimentacao.json`). Os tipos "Novo Cargo" e "Mudança de Função" foram removidos por completo do produto — não aparecem mais no seletor de tipo, não têm mais campos de formulário, e todo o código relacionado (`NovoCargoInfo`, a criação automática de `peopleflow_cargos_custom` ao aprovar um "Novo Cargo", a etapa extra "CEO" da matriz de aprovação) foi apagado, não só ocultado. `peopleflow_cargos_custom` continua existindo só para leitura (cargos que já tinham sido criados assim antes) — não há mais como criar um novo através do fluxo de movimentação.

Em "Nova movimentação", "Cargo solicitado" (Admissão) continua sendo texto livre com sugestão via `<datalist>` dos cargos já cadastrados (`colaboradores.cargo` + `peopleflow_cargos_custom.nome`) — uma admissão pode pedir um cargo inédito. **"Novo cargo" de Promoção agora é um `<select>` fechado**, só cargos já existentes no sistema (sem "Novo Cargo" para criar um cargo do zero, não há mais como uma promoção introduzir um nome de cargo novo).

### Pré-cadastro automático ao concluir uma Admissão

O tipo de movimentação **ADM (Admissão)** agora também pede o **Vínculo** (CLT/PJ/Estágio) do candidato. Quando a última etapa é aprovada (RH), o PeopleFlow cria automaticamente o pré-cadastro do colaborador em `colaboradores` — nome, cargo, departamento, gestor, vínculo e data de admissão, os mesmos dados do formulário da movimentação — via `api/criar-pre-cadastro.ts` (RH-only, service_role, mesmo padrão de `api/atualizar-admissao.ts`). Se "Candidato" não tiver sido preenchido na solicitação, ou já existir alguém com o mesmo nome, nenhuma linha é criada (a movimentação conclui normalmente e o toast explica o motivo).

**Isso é um pré-cadastro, não um cadastro completo**: `cpf` fica como string vazia (é `NOT NULL` no schema do SST, mas sem CPF real ainda) e `nascimento`/`epis`/`exames` ficam vazios — essas colunas continuam exclusivas do SST. Quem completa esses dados é a nova tela **Editar colaborador** no Portal SST (aba Colaboradores → ícone de lápis por linha — ver README dele). Por isso o botão "Novo colaborador" do Portal SST foi removido — ele nunca fez nada (era um `window.alert` de placeholder) e agora a entrada de novo colaborador é sempre pela Admissão aqui no PeopleFlow.

### Sincronização de Promoção, Transferência e Desligamento

Ao concluir a última etapa dessas movimentações, o PeopleFlow também atualiza `colaboradores` (mesma tabela, RH-only via service_role):

- **Promoção**: grava o novo cargo, e — quando o colaborador muda de departamento (ver "Promoção com/sem mudança de departamento" abaixo) — também o novo departamento e o novo gestor.
- **Transferência**: grava o novo departamento e o novo gestor (Transferência sempre muda de departamento — é o próprio conceito do tipo, ver abaixo).
- **Desligamento**: **não** grava `desligado = true` diretamente. Em vez disso, cria uma linha em `peopleflow_desligamento_pendente` com nome/data/motivo/quem aprovou; a efetivação real fica com o Portal SST.

Se o campo relevante do formulário ficar vazio, nada é sincronizado — a movimentação conclui normalmente sem alterar o cadastro. **Alteração Salarial não sincroniza nada**: não há coluna de salário em `colaboradores` — os campos "Salário atual"/"Novo salário" (em Alteração Salarial e agora também em Promoção) são só para constar no histórico da movimentação, preenchidos manualmente pelo gestor solicitante.

Promoção/Transferência recarregam a lista de colaboradores do Supabase (`reload()`) logo em seguida, então a mudança aparece nos dois portais sem precisar dar F5.

#### `atualizacaoInfo`/`admissaoInfo`/`desligamentoInfo` são persistidos (fixado em 2026-07-30)

Até essa correção, esses três objetos (que carregam o que precisa ser sincronizado com `colaboradores` — novo cargo, departamento, gestor etc.) só existiam **em memória**, no navegador de quem clicava em aprovar. Como o fluxo normal tem Gestor Solicitante → Diretor Industrial → RH aprovando em sessões/dias diferentes, essa informação se perdia antes da aprovação final chegar, e a sincronização silenciosamente nunca disparava — sem nenhum erro visível. `peopleflow_movimentacoes` ganhou 3 colunas jsonb (`admissao_info`, `atualizacao_info`, `desligamento_info`) gravadas na criação da movimentação (`criarMovimentacao()`/`toRow()`) e lidas de volta em qualquer sessão (`fromRow()`) — corrigindo a perda de dados entre sessões.

#### Promoção/Transferência só efetivam na "Data prevista" do formulário

A aprovação final de uma Promoção/Transferência **não** aplica mais a troca de cargo/departamento na hora — ela respeita a "Data prevista da movimentação" escolhida no formulário (`AtualizacaoCargoDeptoInfo.dataPrevistaIso`, coluna `sincronizado_em` marca quando a sincronização realmente aconteceu). Não existe job/cron neste projeto (Vercel serverless + Supabase), então a checagem roda a cada carga de dados do app (`efetivarSincronizacoesPendentes()` em `src/repositories/movimentacoesRepository.ts`, chamada em `PortalStoreContext.tsx` no load inicial/reload e em `usePortalData.ts` logo após a aprovação final): toda movimentação "Aprovado" de PRO/TRF cuja data prevista já chegou (ou ficou em branco) e que ainda não foi sincronizada tem a troca aplicada automaticamente em `colaboradores` — sem precisar de nenhuma ação manual do RH. Se a data ainda não chegou, o toast avisa a data em que vai ser aplicada, e a movimentação fica "Aprovado" normalmente até lá.

#### Promoção: com ou sem mudança de departamento, numa única movimentação

Antes, promover alguém para outro departamento exigia duas movimentações separadas (Promoção + Transferência). Agora **Promoção contempla os dois cenários dentro do mesmo formulário**, via a pergunta "O colaborador mudará de departamento?" (Sim/Não):

- **Não** (promoção interna, mesmo departamento): só o gestor atual do colaborador pode abrir a movimentação — o app bloqueia o envio com um erro se `me` for outra pessoa. Fluxo normal de 3 etapas (Gestor Solicitante → Diretor Industrial → RH), gestor não muda.
- **Sim** (promoção com mudança de departamento): o formulário pede "Departamento de destino" (lista) e preenche sozinho "Gestor de destino" (somente leitura, derivado de quem gerencia aquele departamento — ver `gestorDoDepartamento()` em `src/domain/hierarquia.ts`). Só esse gestor de destino pode abrir a movimentação — mesmo bloqueio de envio se não for ele. A etapa "Gestor Solicitante" continua existindo (não é pulada), mas passa a ser resolvida para o **gestor de destino**, não o atual — na prática, o gestor atual nunca precisa (nem consegue) aprovar essa movimentação.

**Transferência** ficou exclusiva para mudança de departamento **sem** evolução de cargo (ex.: "Auxiliar de Serviços Gerais" → "Auxiliar de Produção", mesmo nível) — sempre aberta pelo gestor de destino, mesma validação e mesmo mecanismo de "Gestor Solicitante" resolvido para ele. Se o cargo também muda de nível, a movimentação correta é Promoção (com mudança de departamento), não Transferência — o formulário de Transferência não tem mais campo de cargo.

`gestorDoDepartamento()` resolve "o gestor de um departamento" pelo gestor mais frequente entre os colaboradores daquele departamento (não existe uma coluna própria "gestor do depto" — é sempre derivado de `colaboradores.gestor`). `validarForm()` (`src/domain/formMovimentacao.ts`) faz a validação de verdade (bloqueia o envio); o modal só mostra o mesmo aviso antes de enviar, para feedback imediato.

`AtualizacaoCargoDeptoInfo.novoGestor` (`src/types/domain.ts`) carrega esse gestor de destino até a aprovação final, onde `api/atualizar-cargo-departamento.ts` grava a coluna `gestor` em `colaboradores` junto com cargo/departamento (RH-only, service_role — RLS não libera UPDATE direto do navegador).

### Desligamento em duas etapas (PeopleFlow aprova, SST efetiva)

Concluir a etapa final (RH) de uma movimentação de Desligamento **não desliga ninguém ainda** — só registra a solicitação em `peopleflow_desligamento_pendente` (nome, data prevista, motivo, quem aprovou), gravado direto pelo navegador (tabela exclusiva do PeopleFlow, RLS já libera `authenticated`, sem precisar de service_role).

O Portal SST lê essa tabela e mostra um card **"Desligamento pendente"** no Dashboard dele; clicar num item abre a ficha do colaborador já com a tela "Desligar colaborador" aberta e pré-preenchida (data/motivo). O RH revisa, anexa o ASO demissional se for o caso (fluxo que já existia lá, pergunta "possui mais de 90 dias?") e confirma — só nesse momento `colaboradores.desligado` é gravado de fato, e a linha em `peopleflow_desligamento_pendente` é apagada.

Isso significa: entre a aprovação no PeopleFlow e a confirmação no SST, o colaborador **continua ativo** nos dois portais — a movimentação fica "Aprovado" no PeopleFlow, mas o desligamento em si só existe depois que o RH passa pela tela do SST. Ver README do Portal SST para o lado de lá.

Diferente das demais escritas do PeopleFlow (que vão para tabelas próprias, prefixadas `peopleflow_`), esta é a **primeira gravação direta na tabela `colaboradores`** vinda do próprio app — e como a RLS dela só libera `select` para `authenticated`, a escrita passa por uma Vercel Serverless Function RH-only (`api/atualizar-admissao.ts`, mesmo padrão do `api/desligar-colaborador.ts` do SST): confirma que quem chamou é RH e então usa a `SUPABASE_SERVICE_ROLE_KEY` para atualizar só a coluna `admissao`. **Só funciona em produção (Vercel) ou com `vercel dev`** — em `npm run dev` (Vite puro) a chamada falha, o que é esperado localmente.

### Histórico do colaborador (`/colaboradores`)

A ficha de um colaborador (clique numa linha da tabela) tem uma seção **"Histórico"** ao final, listando toda movimentação já solicitada para ele — admissão, promoção, transferência, alteração salarial, desligamento — mais recente primeiro, com tipo, resumo, status e data. Filtra `movimentacoes` por `colaborador === nome` (mesma fonte usada em Workflow/Aprovadas, sem tabela nova); clicar num item abre a mesma ficha completa (`MovimentacaoDetalhe.tsx`) num Drawer por cima do Drawer do colaborador.

### Ver detalhes e reprovação com justificativa (`/workflow`, `/dashboard`)

Cada card de movimentação (Workflow de aprovação e o widget "Aprovações pendentes" do Dashboard) tem um botão **"Ver detalhes"** que abre a mesma ficha completa usada em Movimentações aprovadas (`src/components/shared/MovimentacaoDetalhe.tsx`, extraído para ser reaproveitado nos dois lugares) dentro de um Drawer — todos os campos do formulário, justificativa da solicitação, trilha de aprovações e documentos gerados, sem sair da lista.

**Reprovar** agora exige uma justificativa: em vez de reprovar direto no clique, abre um modal pedindo o motivo (`ReprovarModal.tsx`), que fica gravado no comentário da etapa reprovada e aparece na trilha ("JUSTIFICATIVA DA REPROVAÇÃO") — mesmo texto exibido tanto no card do Workflow quanto na ficha de detalhes.

### Notificação de movimentação por e-mail (Gmail SMTP)

Toda movimentação dispara e-mail nestes 3 momentos (ver `src/domain/notificacoes.ts`):
- **Nova etapa aguardando aprovação** — ao criar a movimentação (primeira etapa) e a cada aprovação intermediária (próxima etapa) — envia para o **aprovador responsável pela etapa atual** (mesmo `emailOf()` usado em `/acessos`), não para o solicitante.
- **Aprovação final / concluída** — quando a última etapa é aprovada, envia para o **solicitante**.
- **Reprovação** — quando qualquer etapa reprova a movimentação, envia para o **solicitante**, com a justificativa.

O envio (`api/notificar.ts`) usa Gmail SMTP via `nodemailer`, autenticado com `GMAIL_USER` + `GMAIL_APP_PASSWORD` (variáveis de servidor, sem prefixo `VITE_`) — a senha é uma **"Senha de app"** do Google (`myaccount.google.com/apppasswords`, exige verificação em 2 etapas habilitada na conta), não a senha normal do Gmail. Qualquer conta autenticada pode chamar essa function (quem age no fluxo varia por etapa — Gestor, Diretor, CEO ou RH), diferente das demais `api/*.ts` que são RH-only.

**Best-effort, nunca bloqueia o fluxo**: a chamada em `notificacoesRepository.ts` engole qualquer erro, e a function em si responde `200` mesmo quando o envio falha (credencial ausente/errada, Gmail fora do ar etc.) — a movimentação já foi aprovada/reprovada/criada e salva no Supabase antes de disparar o e-mail; se o e-mail não sair, isso nunca aparece pro usuário como falha da ação. Sem `GMAIL_USER`/`GMAIL_APP_PASSWORD` configuradas, o envio é pulado silenciosamente (log no console do servidor).

E-mail em HTML com a identidade do portal (`src/domain/emailTemplate.ts`): logo MSB, cores de `src/index.css` (faixa de destaque azul para pendente, verde para aprovada, vermelha para reprovada) e um bloco com os detalhes da movimentação. O logo vai embutido como anexo inline (`cid:msb-logo`, base64 em `api/_lib/msbLogo.ts`) em vez de imagem remota — funciona em qualquer ambiente sem depender de uma URL pública ou de acesso a `public/assets/` a partir da function. `text` continua sendo enviado junto como fallback para clientes que não renderizam HTML.

### Desligados (`/desligados`, RH-only)

Quando alguém é desligado no **Portal SST** (botão "Desligar colaborador"), esse colaborador aparece automaticamente aqui — os dois portais leem a mesma linha da tabela `colaboradores` (`desligado`, `data_desligamento`, `motivo_desligamento`), não há sincronização própria do PeopleFlow, é a mesma tabela.

Colaboradores desligados somem das telas normais (Colaboradores, headcount do Dashboard, seletor de "Nova movimentação" — ver o filtro `!c.desligado` em `usePortalData.ts` e em `colaboradoresParaSelecao` de `NovaMovimentacaoModal.tsx`) e passam a aparecer só aqui, com:
- Dados do desligamento (data, motivo, quem registrou no SST);
- Histórico completo das movimentações desse colaborador no PeopleFlow (promoções, transferências etc. antes do desligamento);
- Dois campos editáveis, exclusivos do PeopleFlow — **valor da rescisão** e **valor da GRRF** —, salvos em `peopleflow_desligamentos` (colaborador não tem esses campos no SST).

Enquanto rescisão ou GRRF não estiverem preenchidos, o colaborador conta como **pendência** — aparece no badge do menu lateral e num card no Dashboard ("Desligamentos pendentes"), visível só para RH.

### Custos de rescisão por mês (Dashboard, RH-only)

Card com gráfico de barras (`src/components/ui/BarChart.tsx`, SVG puro, sem lib externa) mostrando o custo total de rescisão + GRRF por mês, com a quantidade de desligamentos daquele mês anotada acima de cada barra, seguido de uma tabela com o detalhamento (mês, quantidade, rescisão, GRRF, total). Só aparece quando há pelo menos um mês com desligamento.

O mês de cada desligamento vem de `Colaborador.dataDesligamento` (formato `dd/mmm/aaaa`, ex. `"15/jul/2026"`) convertido para o bucket `aaaa-mm` por `mesIsoFromDataBr()` (`src/domain/dates.ts`); o custo de cada mês soma `valorRescisao`/`valorGrrf` de `peopleflow_desligamentos` para os colaboradores desligados naquele mês (`custosRescisaoPorMes()` em `src/domain/desligados.ts`). Um colaborador desligado sem rescisão/GRRF lançado ainda entra na contagem do mês, só não soma valor — ver a pendência da seção acima.

### Avaliação de experiência (`/avaliacoes`)

Contrato de experiência da MSB é **45+45 dias** (duas etapas, nunca uma terceira renovação — regra da CLT). Cada etapa é uma avaliação de ~20 perguntas (escala 1 a 5, agrupadas por categoria — desempenho, conhecimento técnico, produtividade, cultura, relacionamento, comunicação, proatividade, assiduidade, segurança/qualidade — ver `src/data/perguntasAvaliacaoExperiencia.json`), preenchida pelo gestor imediato do colaborador.

**Pendências automáticas**: com base em `colaboradores.admissao` (campo `admissaoIso` no domínio do app), o sistema calcula qual etapa (se alguma) está pendente para cada colaborador ativo (`pendenciasAvaliacaoExperiencia()` em `src/domain/avaliacaoExperiencia.ts`) — aparece como pendência no Dashboard, no badge do menu lateral e na tela `/avaliacoes`, **só para quem tem o colaborador como gestor imediato** (`colaborador.gestor === conta.nome` — vale tanto para perfil Gestor quanto Diretoria, já que um Diretor também pode ser gestor direto de alguém) ou para RH (vê tudo).

A lista só inclui quem ainda está dentro do contrato de experiência (45+45 dias): **< 45 dias** → nenhuma pendência; **≥ 90 dias** → sai da lista automaticamente, avaliado ou não (a CLT não permite prorrogar além dos 90 dias — passado esse prazo, virar pendência automática deixaria de fazer sentido; um caso perdido nessa janela é trabalho manual do RH, não deste relatório). Entre 45 e 89 dias: pendente "45 dias" enquanto essa avaliação não existir; assim que ela é registrada, a etapa seguinte "90 dias" passa a aparecer pendente automaticamente, com o tempo que resta até o fim do contrato para o gestor completá-la.

**Nota e meta**: nota final = média das respostas (1 a 5) convertida em percentual. A indicação automática (`calcularIndicacao()`) usa metas diferentes por etapa — **45 dias**: ≥ 50% indica Renovar, abaixo disso indica Desligar; **90 dias**: ≥ 60% indica Efetivar, abaixo indica Desligar (as opções de decisão em si também mudam por etapa — `opcoesDecisao()` — 45 dias nunca efetiva, 90 dias nunca renova). A indicação é só uma sugestão: o gestor sempre escolhe a **decisão final** manualmente, pré-selecionada com a indicação; se ele escolher algo diferente (nos dois sentidos — desligar apesar da nota boa, ou manter apesar da nota baixa), uma **justificativa é obrigatória**.

Cada avaliação é um registro histórico imutável em `peopleflow_avaliacoes_experiencia` (RLS permissiva para qualquer autenticado, mesmo padrão de `peopleflow_movimentacoes`) — não há edição depois de salva. Por decisão explícita, o resultado **não** dispara automaticamente uma movimentação de Desligamento; fica só registrado, e o gestor/RH decide separadamente se abre uma solicitação de Desligamento no fluxo normal.

**Dispensa (colaboradores já avaliados fora do sistema)**: mesmo dentro da janela de 45–89 dias, um colaborador pode já ter sido avaliado fora do sistema (ex.: avaliação feita em papel/outra ferramenta antes da implantação deste módulo) — por padrão ele continua aparecendo como pendente. Em vez de fabricar uma nota/decisão que nunca existiu de verdade, a tela `/avaliacoes` tem um botão **"Dispensar"** em cada linha de pendência que registra uma isenção permanente em `peopleflow_avaliacoes_experiencia_dispensas` (nome do colaborador, motivo obrigatório, quem dispensou e quando) — `pendenciasAvaliacaoExperiencia()` exclui qualquer colaborador dispensado da lista inteiramente, sem checar dias nem etapa (ver `DispensarAvaliacaoModal.tsx`).

### Descrição de cargo (`/cargos`, formulário POP-RH-001)

Na tela **Cargos**, a coluna "Descrição de cargo" mostra um link **"Ver descrição"** para todo cargo que já tenha o formulário oficial (POP-RH-001) cadastrado em `peopleflow_descricoes_cargo`. Clicar abre uma ficha com todos os campos do formulário:

Cargo sem o link após rodar o seed provavelmente só precisa de um `UPDATE ... SET cargo_nome = '<nome real>'`.

### Gestão de Desempenho (`/desempenho`) — etapa 1 (estrutura) + etapa 2 (funcionamento da AVD) + complementação (controle de processo) + etapa 2.1 (múltiplos tipos de avaliação) + etapa 3 (PDI) + etapa 4 (Avaliação de Potencial) + etapa 5 (Matriz 9 Box) + etapa 6 (Comitê de Calibração) + etapa 8 (Dashboards e Relatórios) + etapa 9 (Histórico)

Módulo novo, em construção por fases. A etapa 1 entregou a base estrutural (configuração de pesos, catálogo de competências comportamentais, KPIs por cargo). A etapa 2 implementou o **funcionamento de verdade**: RH abre um ciclo de Avaliação de Desempenho, o sistema gera automaticamente a avaliação de cada colaborador ativo, e o gestor preenche notas/resultados com cálculo automático de nota final. A complementação adicionou **controle de processo e rastreabilidade** em cima disso (gerenciamento de ciclos, snapshot completo, autosave, validação de conclusão, auditoria). A etapa 2.1 adaptou a arquitetura pro modelo real da MSB: **3 tipos de avaliação por colaborador elegível no mesmo ciclo** (GESTOR, AUTOAVALIACAO, LIDERANCA), regra de elegibilidade por tempo de empresa, e abriu o acesso ao portal pra colaboradores individuais (perfil restrito, só a própria AVD) — tudo em cima da mesma estrutura de dados, parametrizada por `tipo`, sem recriar cálculo/permissão/auditoria já existentes. A etapa 3 acrescentou o **Plano de Desenvolvimento Individual (PDI)**: gerado automaticamente quando a avaliação GESTOR de um ciclo é concluída, com itens editáveis pelo gestor e uma biblioteca de modelos mantida pelo RH (ver seção própria abaixo). A etapa 4 acrescentou a **Avaliação de Potencial**: módulo independente (não altera a nota da AVD nem o PDI), gerado automaticamente junto com o ciclo, 5 perguntas fixas de escala 1-5, nota = média simples. A etapa 5 acrescentou a **Matriz 9 Box**: posicionamento automático de cada colaborador cruzando a Nota Oficial de Desempenho com a Nota Oficial de Potencial, sem nenhuma tabela nova (view puramente derivada, sem edição manual de posição — ver seção própria abaixo). A etapa 6 acrescentou o **Comitê de Calibração**: RH (que representa o Comitê — não é perfil novo) revisa as avaliações concluídas pelo gestor e, quando necessário, ajusta a média comportamental e/ou a nota de potencial antes de homologar a Nota Oficial — a nota original do gestor nunca é sobrescrita (ver seção própria abaixo). A etapa 8 acrescentou 3 **Dashboards gerenciais** (RH/Gestor/Diretoria), todos read-only e puramente derivados dos dados já existentes, com exportação em CSV e PDF (impressão do navegador), e o rastreio de **devolutiva** (conversa de feedback gestor→colaborador pós-homologação) na ficha AVD (ver seção própria abaixo). A etapa 9 acrescentou o **Histórico**: linha do tempo por colaborador de todos os ciclos já realizados (nota oficial de desempenho/potencial, posição na Matriz 9 Box, status do PDI, data da devolutiva, status do ciclo), aberta também ao perfil Colaborador (só a própria linha do tempo) — 100% derivado, nenhuma tabela ou coluna nova (ver seção própria abaixo). Ainda **sem** cálculo consolidado entre autoavaliação e avaliação do gestor, uso da nota da avaliação da liderança, fluxo de aprovação ou reabertura de ciclo (fica pra próximas etapas).

14 tabelas (`supabase/schema.sql`, seções 8 a 17 — as seções 15, 16 e 17 são só colunas/constraints novas em tabelas já existentes, sem tabela nova; a etapa 9 não adicionou nenhuma seção — é 100% derivada, sem mudança de schema), mesmo padrão RLS/comentários do resto do schema:

- **`peopleflow_config_avaliacao_desempenho`** — linha única (`id = 'default'`), peso de cada bloco (Competências Técnicas/KPIs + Comportamentais) que compõe a nota final — editável pelo RH na aba "Configuração", validação de soma=100% só no cliente.
- **`peopleflow_competencias_comportamentais`** — catálogo corporativo (nome, descrição, status ativa/inativa, ordem de exibição e afirmações avaliativas — `afirmacoes jsonb`, cada afirmação é um registro independente da lista, com botões de incluir/excluir/reordenar na ficha de edição, não um campo de texto único). Escala de avaliação (1 a 5, "Não atende" → "Supera as expectativas") é fixa/igual pra todo mundo — vira constante `ESCALA_COMPORTAMENTAL` em `domain/avaliacaoDesempenho.ts`. Desde a etapa 2.1, uma coluna `categoria` ("Comportamental" | "Lideranca") separa dois catálogos na mesma tabela: "Comportamental" (igual pra todos os cargos, usado nas avaliações GESTOR/AUTOAVALIACAO) e "Lideranca" (5 competências específicas — Comunicação, Apoio e Desenvolvimento, Feedback, Respeito e Relacionamento, Organização e Direcionamento — usadas só na avaliação LIDERANCA). A aba "Competências comportamentais" tem um alternador pra trocar qual catálogo está sendo visto/editado; a competência nova já nasce com a categoria selecionada.
- **`peopleflow_kpis_cargo`** — KPIs (Competências Técnicas) **por cargo**, nunca reaproveitando as competências da Descrição de Cargo nem competências genéricas. Carga inicial a partir de planilha real do RH ("Metas AVD S1_2026.xlsx") — ver de-para de nomenclatura abaixo.
- **`peopleflow_ciclos_avaliacao_desempenho`** — ciclo aberto pelo RH (nome, período de referência, data de início/encerramento, `status` "Aberto"/"Encerrado"). Ao criar, gera automaticamente 1 linha em `peopleflow_avaliacoes_desempenho` por colaborador ativo (elegibilidade nesta etapa: todo colaborador ativo, sem regra de tempo mínimo de empresa ainda). RH encerra o ciclo na tela "Ciclos" (dentro de `/desempenho`) — isso **trava todas as avaliações vinculadas de uma vez**, mesmo as "Em andamento"; sem reabertura ainda.
- **`peopleflow_avaliacoes_desempenho`** — `ciclo_id` referencia o ciclo; `resultados_comportamentais`/`resultados_kpis` guardam o conjunto de competências/KPIs **travado no momento da criação** (não recalculado depois, mesmo que o catálogo mude — evita que uma avaliação em andamento mude de "tamanho" no meio do caminho), com **snapshot completo**: nome/descrição/afirmações da competência e nome/descrição/meta/unidade/sentido/peso do KPI são copiados pra dentro do próprio jsonb no momento da criação (`competenciaNome`/`competenciaDescricao`/`afirmacoes` em cada item de `resultados_comportamentais`; `kpiNome`/`kpiDescricao`/`meta`/`unidadeMedida`/`sentidoMeta`/`peso` em cada item de `resultados_kpis`) — ficam congelados durante todo o ciclo, mesmo que o cadastro original seja editado ou o item seja desativado/excluído depois. As funções de cálculo (`notaKpi`/`mediaTecnica`/`itensPendentes` em `domain/avaliacaoDesempenho.ts`) usam esse snapshot como fonte primária, com lookup no catálogo atual só como fallback pra avaliações antigas geradas antes desse snapshot existir. `cargo`/`departamento`/`gestor_avaliador` são **snapshot da estrutura organizacional no momento da geração** — preservam o histórico mesmo que o colaborador seja promovido ou troque de gestor depois. Desde a etapa 2.1, duas colunas a mais: `tipo` (`"GESTOR" | "AUTOAVALIACAO" | "LIDERANCA"` — mesma estrutura pros 3, diferenciados só por este campo) e `avaliado` (quem está sendo avaliado nesta ficha — igual a `colaborador_nome` em GESTOR/AUTOAVALIACAO; em LIDERANCA é o gestor cujo estilo de liderança está sendo avaliado, também congelado — `colaborador_nome` continua sendo sempre o liderado "dono" do conjunto de até 3 fichas geradas pra ele naquele ciclo). Colaborador sem gestor cadastrado nasce com `gestor_avaliador` vazio na ficha GESTOR (e sem ficha LIDERANCA — não existe gestor pra avaliar) — só o RH vê/trata essa ficha; a tela "Ciclos" mostra um badge "N sem gestor" por ciclo, e a lista de Avaliações tem um filtro RH-only "Somente sem gestor". `nota_final`/`media_tecnica`/`media_comportamental` são recalculados e regravados a cada save (`notaFinalPorTipo()` trata LIDERANCA à parte — sem KPI, a "nota final" dela é a própria média comportamental, não a ponderação normal) — junto com `criado_em`/`concluido_em`, formam a base do histórico do colaborador. **Validação contra duplicidade**: `criarCicloComAvaliacoes()` confere no banco quais (`tipo`, `colaborador_nome`) já existem pra aquele `ciclo_id` antes de inserir — nunca insere uma segunda ficha do mesmo tipo pro mesmo colaborador no mesmo ciclo.
- **`peopleflow_log_avaliacao_desempenho`** — auditoria básica, append-only: ciclo criado/encerrado, avaliações geradas, avaliação iniciada/salva/concluída, colaborador não elegível (usuário + timestamp). Gravação **best-effort** — nunca lança, só loga no console em caso de falha (`logAvaliacaoDesempenhoRepository.ts`, mesmo espírito do `sst_log` do Portal SST) — nunca bloqueia a ação principal. Exibido como lista crua colapsável dentro da linha de cada ciclo na tela "Ciclos" (RH) — sem dashboard/relatório novo. A data de início de cada avaliação (coluna "Início" na lista de Avaliações) também é derivada daqui (1º registro "AVALIACAO_INICIADA"), sem precisar de um campo dedicado.
- **`peopleflow_pdi`** (cabeçalho do plano, etapa 3) — 1 por colaborador por ciclo, gerado automaticamente na conclusão da avaliação **GESTOR** (nunca por AUTOAVALIACAO/LIDERANCA). `gestor_responsavel` é um **snapshot** do `gestorAvaliador` da avaliação que originou o plano — mesma lógica de congelamento já usada na AVD, garante que quem preencheu a avaliação não perca o direito de editar o PDI numa transferência futura. `status` (`"Não iniciado" | "Em andamento" | "Concluído"`) é do plano inteiro; colunas antigas (`acao`/`prazo`/`responsavel`/`origem`, de um placeholder da etapa 1 nunca usado de verdade) ficam vestigiais, sem leitura pelo código novo.
- **`peopleflow_pdi_itens`** — 1 por competência comportamental/KPI abaixo da `nota_minima_pdi` configurável (config em `peopleflow_config_avaliacao_desempenho`, padrão 3) na avaliação que gerou o plano, ou adicionado manualmente pelo gestor depois. Cada item tem objetivo de desenvolvimento (sugerido automaticamente, editável), responsável (Colaborador/Gestor/Ambos — só informativo), datas de início/conclusão prevista, status próprio e observações. `competencia_id` usa o id estável do catálogo (Comportamental) ou fica vazio (Tecnica, sem id estável entre cargos — usa `competencia_nome`).
- **`peopleflow_pdi_acoes`** — lista de ações de desenvolvimento por item, sem limite, CRUD livre (descrição/responsável/prazo/status). "Concluir o PDI" só fica disponível quando existe pelo menos 1 ação no plano inteiro e todas estão Concluída ou Cancelada (evita que um plano recém-gerado, ainda vazio, seja "concluível" na hora).
- **`peopleflow_pdi_biblioteca`** — biblioteca de modelos mantida pelo RH (aba "Biblioteca de PDI"): por competência comportamental (chave = id estável do catálogo) ou KPI (chave = nome do indicador), um objetivo de desenvolvimento sugerido + lista de ações sugeridas, usados por `sugerirObjetivoEAcoes()` (`domain/pdi.ts`) ao gerar um PDI automaticamente. Sem modelo cadastrado pra aquela competência/KPI, o item nasce com um objetivo genérico e nenhuma ação sugerida.
- **`peopleflow_avaliacoes_potencial`** (etapa 4) — **módulo independente da AVD**: 1 avaliação por colaborador elegível, gerada automaticamente junto com o ciclo (mesma elegibilidade da AVD), com 5 perguntas fixas (`respostas jsonb`, cada uma com `perguntaId`/`pergunta` — snapshot do texto no momento da geração — /`nota`) numa escala 1-5 (mesma `ESCALA_COMPORTAMENTAL` da AVD). `nota_potencial` = média simples das respostas já dadas, recalculada a cada gravação (`calcularNotaPotencial()` em `domain/avaliacaoPotencial.ts`, ponto único de cálculo — nunca recalculada em outro lugar). `cargo`/`departamento`/`gestor_avaliador` são snapshot, mesma lógica da AVD (`gestor_avaliador` vazio quando o colaborador não tinha gestor — RH trata). Nunca altera `nota_final`/`media_*` da AVD nem o PDI. Desde a etapa 5, `constraint unique (ciclo_id, colaborador_nome)` reforça no banco o que antes só era garantido por uma checagem de aplicação — a Matriz 9 Box depende de no máximo 1 ficha Concluída por colaborador/ciclo aqui (mesma constraint em `peopleflow_avaliacoes_desempenho`, `unique (ciclo_id, tipo, colaborador_nome)`). Desde a etapa 6, ganhou as colunas de calibração descritas abaixo.
- **Colunas de calibração (etapa 6)** — 8 colunas novas em cada uma de `peopleflow_avaliacoes_desempenho`/`peopleflow_avaliacoes_potencial` (sem tabela nova): `status_calibracao` (`"Não iniciada" | "Aguardando Calibração" | "Homologada"` — campo **independente** de `status`, que nunca muda de significado), `media_comportamental_calibrada`/`nota_potencial_calibrada` (override do RH, `null` = sem calibração), `nota_final_oficial`/`nota_oficial` (a Nota Oficial, calculada só na homologação), `justificativa_calibracao`, `calibrado_por`/`calibrado_em`, `homologado_por`/`homologado_em`. `nota_final`/`nota_potencial` (do gestor) nunca são sobrescritos — o histórico completo (nota inicial, nota oficial, quem/quando calibrou e homologou) fica preservado só por ter dois campos separados na mesma linha.
- **Colunas de devolutiva (etapa 8)** — 3 colunas novas em `peopleflow_avaliacoes_desempenho` (sem tabela nova): `devolutiva_realizada` (boolean, default `false`), `devolutiva_por`, `devolutiva_em`. Só relevantes pra ficha tipo GESTOR já `status_calibracao = 'Homologada'` — marca que a conversa de feedback gestor→colaborador pós-homologação já aconteceu. Sem "desmarcar" no fluxo atual.

**Geração e permissões da Avaliação de Potencial (etapa 4)**: gerada como um **3º passo sequencial best-effort** dentro de `criarCicloAvaliacaoDesempenhoFn()` — depois do ciclo e das fichas da AVD já criados com sucesso, um `try/catch` próprio chama `criarAvaliacoesPotencial()` (dedup por `colaborador_nome` dentro do `ciclo_id`, mesmo padrão de `criarCicloComAvaliacoes()`); uma falha aqui não desfaz a abertura do ciclo, só avisa via toast (mesmo espírito da geração do PDI). `avaliacoesPotencialVisiveis`: RH vê tudo; senão, só quem é gestor **atual** do colaborador — o próprio colaborador **nunca** vê a própria ficha (checagem explícita e incondicional, antes de qualquer outra — regra mais restrita que a AVD, que ao menos deixa Gestor/Diretoria verem a própria ficha GESTOR). `podeEditarAvaliacaoPotencial()`: RH sempre, checado primeiro e incondicionalmente (diferente da AVD, que bloqueia até o RH quando o ciclo está encerrado — aqui isso seria um beco sem saída depois de reabrir uma ficha de ciclo já encerrado); senão, só quem `gestorAvaliador` aponta (congelado, igual à AVD, sem a união frozen+atual que o PDI usa), e só enquanto não "Concluída" e o ciclo não estiver "Encerrado". RH pode reabrir uma ficha concluída a qualquer momento, mesmo com o ciclo encerrado (`reabrirAvaliacaoPotencial()`). Aba "Potencial" dentro de `/desempenho`, aberta a todo perfil MENOS "Colaborador" (RH/Gestor/Diretoria) — categoria de visibilidade de aba (`ABAS_GESTAO` em `GestaoDesempenhoPage.tsx`), distinta das já existentes RH-only e "aberta a todos".

**Matriz 9 Box (etapa 5, atualizada na etapa 6)** — `domain/matriz9Box.ts` + aba "Matriz 9 Box" (mesma categoria `ABAS_GESTAO` do Potencial). **View puramente derivada, sem tabela própria e sem edição manual de posição** — cruza ao vivo a **Nota Oficial** da ficha GESTOR (Desempenho) com a **Nota Oficial** da ficha de Potencial (Potencial) do ciclo selecionado; desde a etapa 6, o filtro é por `statusCalibracao === "Homologada"` nas duas fichas (não mais `status === "Concluída"` — uma ficha só concluída pelo gestor, mas ainda não homologada pelo Comitê de Calibração, não é definitiva), lendo `notaFinalOficial`/`notaOficial` (nunca `notaFinal`/`notaPotencial` do gestor) — "consumir exclusivamente a Nota Oficial, nunca a nota inicial do gestor". Sem uma das duas fichas Homologadas, o colaborador simplesmente não aparece plotado (mensagem de transparência explica se é por avaliação ainda não concluída ou por aguardar homologação). Classificação em Baixo/Médio/Alto por 4 limiares configuráveis pelo RH (`matriz_desempenho_limite_medio`/`_alto`, `matriz_potencial_limite_medio`/`_alto` em `peopleflow_config_avaliacao_desempenho`, padrão 3/4 nos dois eixos — `classificarFaixaMatriz9Box()`, corte `>=` nos dois limiares) e posicionada num dos 9 quadrantes, com nomenclatura corporativa fixa sugerida e aprovada pelo RH (`NOMES_QUADRANTES_MATRIZ_9_BOX`): Alto Potencial/Baixo Desempenho = "Desenvolver com Prioridade", .../Médio = "Talento em Desenvolvimento", .../Alto = "Talento Estratégico"; Potencial Médio/Baixo = "Reavaliar Desempenho", .../Médio = "Contribuidor Consistente", .../Alto = "Alto Desempenho"; Baixo Potencial/Baixo = "Atenção Imediata", .../Médio = "Estável", .../Alto = "Especialista Consolidado". Filtros de ciclo (também serve de "histórico por ciclo" — trocar o ciclo recalcula a grade toda, sem view separada), departamento, gestor, cargo e status (Ativo/Inativo/Todos, padrão Ativo). Clique num marcador abre um Drawer **só leitura** (Nota Oficial de Desempenho/Potencial, quadrante, ciclo) — reforça que toda mudança de posição só acontece calibrando/atualizando a AVD/Potencial de origem. Visibilidade (`colaboradoresParaMatriz9Box` em `usePortalData.ts`): RH vê todos (incl. desligados); Gestor/Diretoria só quem tem `gestor === me` (mesma regra do Potencial, não a de `colaboradoresListagem`); Colaborador, nunca. Reforço de unicidade no banco (`unique (ciclo_id, tipo, colaborador_nome)`/`unique (ciclo_id, colaborador_nome)`) garante que o join da matriz sempre encontre no máximo 1 ficha por colaborador/ciclo em cada tabela.

**Comitê de Calibração (etapa 6)** — `domain/calibracao.ts` + aba "Calibração" (RH-only — o Comitê é sempre o RH, spec não menciona Gestor/Diretoria nesta aba em nenhum momento, diferente de Potencial/Matriz 9 Box). O fluxo de calibração vive num campo **independente**, `statusCalibracao` (tanto na AVD quanto na Potencial) — o `status` original (`"Concluída"` etc.) nunca muda de significado, só indica se o gestor terminou de preencher; renomear o enum compartilhado (usado também por AUTOAVALIACAO/LIDERANCA e por toda a UI já existente) para bater literalmente com os 5 estágios do spec exigiria trocar a mesma string em várias telas com risco real de esquecer um ponto, então o resultado funcional é idêntico sem esse risco. **Gatilho automático**: sempre que a ficha GESTOR (nunca AUTOAVALIACAO/LIDERANCA) e a ficha de Potencial do mesmo colaborador/ciclo estão AMBAS `status === "Concluída"` e nenhuma delas ainda entrou em calibração, as duas viram `statusCalibracao: "Aguardando Calibração"` juntas — o gatilho roda dentro de `salvarAvaliacaoDesempenhoFn`/`salvarAvaliacaoPotencialFn` (qualquer um dos dois lados, o que for concluído por último, dispara a checagem), passando o objeto recém-salvo direto pro gatilho em vez de relê-lo de `state` logo depois do próprio `dispatch` (que ainda não teria propagado — só o lado que NÃO acabou de ser salvo é lido de `state`). Na aba Calibração, RH vê Dados Gerais + AVD (Média Técnica/Comportamental/Nota Final, tudo do gestor, só leitura) + Potencial (Nota Final, só leitura) + prévia ao vivo da posição na Matriz 9 Box, e pode calibrar 2 números — **Média Comportamental** e **Nota de Potencial** (ambos opcionais, em branco = mantém o original) — nunca os KPIs/média técnica ("resultado objetivo, não sofre calibração") nem as respostas individuais das afirmações. Justificativa é obrigatória só se alguma nota realmente mudou (`validarCalibracao()`/`precisaJustificativa()`, comparação arredondada pra não disparar por ruído de ponto flutuante). Um clique em "Homologar Avaliação" (`homologarCalibracao()`) calcula a Nota Oficial das duas fichas (`calcularNotaOficialAvd()`/`calcularNotaOficialPotencial()` — reaproveita `notaFinalAvaliacao()`, nunca duplica a fórmula), grava as duas de uma vez, e `statusCalibracao` vira `"Homologada"` — travado depois disso, sem reabertura nesta etapa (o spec não pede uma pra este fluxo, diferente do PDI/Potencial). **Segurança**: `podeCalibrarAvaliacaoDesempenho()` é RH-only e só quando `statusCalibracao === "Aguardando Calibração"`; `podeEditarAvaliacaoPotencial()`/`reabrirAvaliacaoPotencial()` ganharam um guard novo (`statusCalibracao !== "Não iniciada"` bloqueia) — sem ele, o bypass incondicional que RH já tinha nesses dois (existente desde a etapa 4, pra permitir reabrir mesmo com o ciclo encerrado) deixaria o RH contornar a calibração inteira editando a ficha de Potencial pelo caminho antigo, sem justificativa nem rastro (a AVD já era seguro — `podeEditarAvaliacaoDesempenho()` bloqueia `status === "Concluída"` **antes** de checar RH, sem bypass nenhum). Histórico (Nota Inicial do Gestor, Nota Oficial, justificativa, quem/quando calibrou e homologou) fica disponível pro RH na própria aba, sem tabela extra — nada é sobrescrito.

**Dashboards e Relatórios (etapa 8)** — `domain/dashboardDesempenho.ts` + aba "Dashboard" (categoria `ABAS_GESTAO`, aberta a RH/Gestor/Diretoria). 3 painéis **read-only, puramente derivados** dos dados já existentes — nenhuma agregação é persistida. `DashboardRHTab.tsx`/`DashboardGestorTab.tsx`/`DashboardDiretoriaTab.tsx` usam `colaboradoresListagem` (não `colaboradoresParaMatriz9Box`) como fonte de população: essa getter já dá empresa toda pra RH **e Diretoria**, e só a própria equipe (`gestor === me`) pro Gestor — uma exceção deliberada ao padrão do resto do módulo (em todo o resto, Diretoria é tratada igual Gestor), coerente com o "painel executivo" que o Dashboard da Diretoria pede. Todas as métricas de nota (média geral/por setor, evolução por ciclo, distribuição por faixa, Matriz 9 Box) exigem `statusCalibracao === "Homologada"` e usam a Nota Oficial — nunca a nota bruta do gestor, mesma regra da etapa 6; métricas de competência/KPI individuais só exigem `status === "Concluída"` (dado bruto, nunca tocado pela calibração) e sempre filtram `tipo === "GESTOR"` (senão AUTOAVALIACAO/LIDERANCA contaminariam uma métrica "organizacional"). O filtro de ciclo nunca oferece "Todos" (mesmo precedente do `Matriz9BoxTab.tsx`) — evita contar a mesma pessoa 2x numa distribuição; só "Evolução por ciclo" ignora esse filtro (é o único bloco que sempre olha todos os ciclos). Ranking de KPIs (`mediasPorKpi()`) agrupa por `kpiNome` **+ cargo**, não só `kpiNome` — `KpiCargo` não tem id estável entre cargos, então dois cargos podem ter um KPI de mesmo nome medindo coisas diferentes; o cargo aparece junto ao nome no ranking como mitigação (mesma simplificação já aceita na Biblioteca de KPI do PDI). Blocos de PDI fazem join com `Colaborador` via `Pdi.colaboradorNome` (`Pdi` não tem `departamento`/`cargo` próprios) e usam o `.gestor` **vivo** do colaborador pro filtro de gestor, nunca o `gestorResponsavel` congelado do PDI (pode divergir após uma transferência). Exportação: `lib/exportacaoCsv.ts` (`gerarCsv`/`baixarArquivo`, zero dependências novas — Blob + `URL.createObjectURL` + `<a>` temporário, com escaping RFC4180 pra campos com vírgula/aspas/quebra de linha) pro CSV, e `window.print()` pro PDF — um par de regras `@media print` global (`AppShell.module.css`/`Header.module.css`, escondem Sidebar/Header em qualquer página do portal, não só nos dashboards) resolve o layout de impressão sem duplicar CSS por dashboard. Devolutiva: `marcarDevolutivaRealizadaFn()` em `usePortalData.ts`, permitido pra RH ou quem `gestorAvaliador` aponta, só quando `statusCalibracao === "Homologada"` — deliberadamente **sem** o gate de ciclo-encerrado que `podeEditarAvaliacaoDesempenho()` tem (mesmo precedente de `homologarCalibracao()`, que também não tem esse gate: a ação acontece naturalmente perto do fechamento do ciclo). Bloco "Calibração" no `AvaliacaoDesempenhoDrawer.tsx` (visível só pra ficha tipo GESTOR já calibrada) mostra o status, a Nota Oficial e o controle de devolutiva.

**Histórico (etapa 9)** — `domain/historicoDesempenho.ts` + aba "Histórico" (categoria
`ABAS_ABERTAS`, aberta a TODO perfil incl. Colaborador — a ÚNICA aba deste grupo que
compartilha visibilidade com dados antes restritos a RH/Gestor/Diretoria; ver
`GestaoDesempenhoPage.tsx`). Linha do tempo por colaborador de todos os ciclos já
realizados (nome do ciclo, datas de início/encerramento, Nota Oficial de Desempenho,
Nota Oficial de Potencial, posição na Matriz 9 Box, status do PDI, data da devolutiva,
status do ciclo) — **100% derivado, nenhuma tabela ou coluna nova**. A garantia de
integridade histórica que o spec desta etapa pede ("nenhuma informação poderá ser
sobrescrita... ao recalibrar/reabrir/atualizar, preservar a versão homologada") já é
garantida pela arquitetura de permissões das etapas anteriores, sem precisar de
auditoria/versionamento novo: uma vez `statusCalibracao === "Homologada"`, não existe
nenhum caminho no app que edite a ficha de novo (`podeCalibrarAvaliacaoDesempenho()`
só libera calibrar quando `"Aguardando Calibração"`, nunca `"Homologada"`;
`reabrirAvaliacaoPotencial()` bloqueia assim que `statusCalibracao !== "Não
iniciada"`; e a ficha AVD tipo GESTOR não tem nenhuma função de reabertura). Como na
Matriz 9 Box, a posição é sempre recalculada ao vivo com os limiares ATUAIS da
configuração — nunca houve snapshot de limiares por ciclo em nenhuma etapa anterior,
e não é o tipo de informação que o spec pede pra preservar (ele fala de notas de
avaliação, não de configuração). `colaboradoresParaHistorico` (`usePortalData.ts`) —
RH e Diretoria veem a empresa toda incl. desligados (decisão confirmada com o
usuário: o spec desta etapa só lista permissões pra RH/Gestor/Colaborador, omitindo
Diretoria — tratada aqui como RH, ao contrário do resto do módulo, que trata
Diretoria igual Gestor); Gestor só quem tem `gestor === me`; Colaborador vê o próprio
registro (não `[]` como em `colaboradoresParaMatriz9Box`). `HistoricoTab.tsx`: RH/
Gestor/Diretoria veem uma tela de consulta (busca por nome + filtros Gestor/Setor/
Cargo/Status Ativo-Inativo/Ciclo — o filtro de ciclo aqui aceita "Todos" sem risco de
dupla-contagem, já que cada linha da lista é 1 colaborador, não 1 nota agregada) e
clicam num colaborador pra abrir `HistoricoDrawer.tsx` com a linha do tempo completa;
Colaborador pula direto pra própria linha do tempo (`HistoricoLinhaDoTempo.tsx`,
componente compartilhado pelos dois casos), sem lista/filtro — o spec já enquadra a
visão dele como "sua própria linha do tempo", não uma busca.

**Permissões do PDI** (`pdiVisiveis`/`podeEditarPdi` em `usePortalData.ts`): RH vê e edita tudo (inclusive reabrir um PDI concluído). O dono (`colaboradorNome === eu`) só vê depois de `"Concluído"` — diferente da AVD, aqui é só uma questão de tempo, não uma restrição permanente. Quem é gestor **atual** do dono vê sempre. Edição é liberada pra quem `gestor_responsavel` aponta (o gestor congelado no momento da geração) **ou** o gestor atual (união dos dois — cobre continuidade de quem originou o plano e praticidade de um gestor novo assumir sem precisar do RH), sempre que o plano não estiver `"Concluído"`. Geração automática é protegida contra duplicidade por uma checagem direta no Supabase (não no estado local) antes de inserir — cobre o caso real de RH e o gestor concluindo a mesma avaliação quase ao mesmo tempo. Editar um PDI existente (`salvarPdi()`, estratégia "apagar tudo e reinserir" os itens/ações) tem uma **trava de concorrência otimista** via `updated_at` — se alguém salvou por cima entre a leitura e a gravação, a UI avisa em vez de apagar o trabalho da outra pessoa silenciosamente.

**Elegibilidade e os 3 tipos de avaliação (etapa 2.1)**: ao abrir um ciclo, `elegivelParaCicloAvaliacaoDesempenho()` (`domain/avaliacaoDesempenho.ts`) reprova quem está desligado ou tem menos de 6 meses completos de empresa até a data de corte (a `dataEncerramento` do ciclo) — `mesesCompletos()` em `domain/dates.ts` faz a conta por parsing manual de string, mesmo padrão do resto do arquivo. Quem não é elegível não recebe nenhuma ficha; o motivo vira um log `COLABORADOR_NAO_ELEGIVEL`. Pra cada colaborador elegível, `criarCicloAvaliacaoDesempenhoFn()` (`usePortalData.ts`) gera: 1 **AUTOAVALIACAO** (mesma estrutura da ficha do gestor — competências comportamentais + KPIs do cargo + comentários — mas sua nota nunca compõe a nota oficial, serve só de reflexão/apoio à reunião de feedback); 1 **GESTOR** (nota oficial da AVD, sem mudança de regra desde a etapa 2); e, só se o colaborador tiver gestor cadastrado, 1 **LIDERANCA** (usa exclusivamente o catálogo de competências categoria "Lideranca", sem KPI — o liderado avalia o próprio gestor).

**Acesso ao portal e visibilidade (etapa 2.1)**: `Perfil` ganhou um 4º valor, `"Colaborador"` — acesso restrito a quem não é RH/Diretoria/gestor de ninguém. `buildAccess()` (`domain/hierarquia.ts`) continua exatamente como antes (RH/Diretoria/gestor real — alimenta a tela "/acessos" já existente, sem mudança); uma nova `buildAccessAvd()` lista separadamente quem é elegível só pro acesso restrito da AVD (ativo, 6+ meses de empresa, ainda não coberto por `buildAccess()`) — nova aba RH-only "Acessos AVD" dentro de `/desempenho` (não mistura com a tela "/acessos" principal), backed por `api/listar-acessos-avd.ts`; o provisionamento em si (`api/provisionar-acesso.ts`) é o mesmo endpoint pras duas listas. `useConta()` tenta `buildAccess()` primeiro e cai pra `buildAccessAvd()` se não achar. Perfil "Colaborador" só alcança `/desempenho` — checagem centralizada em `AppShell.tsx` (redireciona qualquer outra rota pra lá) em vez de guarda espalhada por página, e a `Sidebar` mostra um menu mínimo ("Minhas Avaliações") pra esse perfil. Visibilidade de cada ficha (`avaliacoesDesempenhoVisiveis` em `usePortalData.ts`): RH vê tudo; cada um vê suas próprias 3 fichas do ciclo, exceto a ficha GESTOR sobre si mesmo, que fica oculta pro perfil "Colaborador" (nunca vê a nota/comentário que o gestor deu) mas visível pra Gestor/Diretoria; e quem é gestor de alguém vê as até 3 fichas desse liderado (mas só edita a do tipo GESTOR — `podeEditarAvaliacaoDesempenho()` não precisou mudar, já concede edição só a quem `gestorAvaliador` aponta). **Atenção de segurança**: como em todo o PeopleFlow, a proteção de quem vê o quê é só no código do app — RLS do Supabase libera qualquer autenticado (`for all using (true)`). Isso era um risco aceitável quando só RH/Diretoria/gestores logavam; abrir acesso a todo colaborador elegível amplia bastante essa exposição (tecnicamente, alguém com acesso ao próprio token consegue ler/escrever direto no Supabase, ignorando as regras de visibilidade do app). Fica como recomendação de próximo passo — RLS de verdade, restringindo cada linha por quem está logado — não implementado nesta etapa.

**Ponto único de cálculo**: `calcularNotasAvaliacao(avaliacao, kpisCargo, config)` (`domain/avaliacaoDesempenho.ts`) é a **única** função que produz `{mediaTecnica, mediaComportamental, notaFinal}` — usada idêntica no preview ao vivo do Drawer, ao salvar/concluir a avaliação e na coluna "Nota final" da lista de Avaliações, evitando qualquer divergência entre o que é exibido e o que é gravado. Validação de negócio independente de UI: `validarConfigAvaliacaoDesempenho()` (soma dos pesos = 100%), `validarNotaMinimaPdi()` (1 a 5) e `validarLimiaresMatriz9Box()` (1 a 5, limiar médio < limiar alto) rodam dentro de `atualizarConfigAvaliacaoDesempenhoFn()` **antes** de qualquer gravação no Supabase — bloqueiam configuração inválida não importa por onde a função seja chamada (frontend, API ou integração futura), não só uma checagem solta na tela de Configuração. Desde a etapa 5, `atualizarConfigAvaliacaoDesempenho()` recebe um objeto de config (não mais parâmetros posicionais — 3ª extensão desse config, 8 números posicionais era um risco real de troca de ordem silenciosa); a camada de repositório recebe `editadoPor` do chamador (padrão de sempre), a de hook injeta `me` internamente como todo outro `*Fn` de escrita. Aproveitando essa rodada, corrigido um bug da etapa 3: o campo "Nota mínima para o PDI" tinha estado/validação mas nunca foi de fato renderizado em `ConfiguracaoAvaliacaoTab.tsx` — RH nunca conseguiu editá-lo.

**Cálculo** (`src/domain/avaliacaoDesempenho.ts`, funções puras):
- Cada afirmação recebe nota de 1 a 5; a nota da competência é a média das afirmações respondidas; a média comportamental geral é a média das competências já completas.
- Percentual de atingimento de um KPI: "Maior é Melhor" → `resultado/meta×100`; "Menor é Melhor" → `meta/resultado×100` (lógica invertida — resultado igual ou menor que a meta já é ≥100%). Percentual vira nota pela escala ≥95%→5, 93-94,99%→4, 90-92,99%→3, 85-89,99%→2, <85%→1.
- Média das Competências Técnicas é ponderada por `peso` de cada KPI (`peso ?? 1`) — quando nenhum KPI tem peso definido, isso já dá exatamente a média simples pedida na especificação, sem precisar de um branch separado pros dois casos.
- Nota final da avaliação pondera as duas médias pelos pesos de `ConfigAvaliacaoDesempenho`.
- Status avança sozinho conforme o gestor preenche — "Não iniciada" → "Em andamento" (ao salvar progresso, manual ou automático) → "Concluída" (ao concluir, só disponível quando toda afirmação/KPI tem valor) — e **trava a edição por completo** depois de concluída, ou se o ciclo for encerrado antes disso; só uma futura funcionalidade de reabertura de ciclo desfaz isso.
- `itensPendentes(avaliacao, competencias, kpis)` lista textualmente o que falta pra poder concluir (ex.: "Comunicação — afirmação 2", "KPI: OTIF") — exibida no Drawer em vez de só desabilitar o botão "Concluir avaliação" em silêncio.

**Autosave e recuperação** (`AvaliacaoDesempenhoDrawer.tsx`): qualquer edição (nota, resultado de KPI, comentário) agenda uma gravação automática ~1,2s depois da última mudança, usando a mesma função de salvar do botão manual — sem toast a cada gravação, só um indicador textual discreto ("Salvando..." / "Salvo automaticamente às HH:MM"). A 1ª gravação (manual ou automática) já promove a avaliação de "Não iniciada" para "Em andamento" sozinha. "Recuperar a última versão salva" é o comportamento natural do Drawer (sempre parte do que está persistido no Supabase) — não precisou de lógica adicional.

**De-para da planilha de KPIs**: a planilha agrupa alguns cargos que compartilham o mesmo conjunto de KPIs sob um rótulo combinado (ex.: "Analista de Planejamento e Assistente de Planejamento", "Analista Contábil e Analista Financeiro") — como a instrução foi explícita ("cada cargo deverá possuir apenas os KPIs definidos para ele"), essas linhas foram **duplicadas por cargo real** em vez de criar um conceito de "grupo" (`supabase/seed_kpis_cargo.local.sql`, gitignorado — dado real da empresa). Nomes/tipos/metas foram copiados exatamente como na planilha, sem alterar nomenclatura. Cargos do catálogo sem KPI definido na planilha (Analista Administrativo, Assistente de Produção, Consultor de Vendas, Diretor Geral - CEO, Estagiário (a), Jovem Aprendiz Administrativo, Jovem Aprendiz Industrial, Líder de Produção, Supervisor (a) de Operações de Vendas, Técnico de Manutenção) ficam sem KPI por ora — esperado, não é erro.

**Acesso à página**: `/desempenho` é alcançável por qualquer perfil autenticado desde a etapa 2.1 (antes era RH-only — Gestor/Diretoria nunca tinham conseguido chegar lá, nem pelo link do menu nem digitando a URL, o que na prática travava o preenchimento da ficha GESTOR desde a etapa 2). `podeVerCadastros` (`navRegistro()` em `domain/permissoes.ts`) é **RH-only** — diferente de outras telas do portal (ex.: `colaboradoresListagem`), Diretoria não tem nenhum acesso especial dentro deste módulo. As abas "Configuração"/"Competências comportamentais"/"Competências técnicas"/"Acessos AVD"/"Biblioteca de PDI" são RH-only; "Avaliações" e "PDI" são abertas a todos os perfis (incl. Colaborador) — RH vê a seção "Ciclos" (lista administrativa completa + abrir/encerrar ciclo + log de auditoria) e todos os PDIs, Gestor/Diretoria preenchem as fichas dos liderados e veem/editam os PDIs de quem lideram, e o perfil "Colaborador" só enxerga essas duas abas, com suas próprias fichas (e o próprio PDI, só depois de concluído pelo gestor); "Potencial" (etapa 4) é aberta a todo perfil MENOS "Colaborador" — uma 3ª categoria de visibilidade de aba (`ABAS_GESTAO` em `GestaoDesempenhoPage.tsx`), já que hoje Gestor e Diretoria só enxergavam exatamente as mesmas abas que o Colaborador antes desta etapa. Preencher/concluir uma ficha específica é liberado pro RH (qualquer uma) ou por quem `gestorAvaliador` aponta como responsável (`podeEditarAvaliacaoDesempenho()` em `usePortalData.ts`) — e só enquanto ela não estiver "Concluída" e o ciclo não estiver "Encerrado". A lista de Avaliações tem filtros por ciclo/status/tipo/departamento; RH também vê a coluna "Avaliador".

```
    movimentacoesRepository.ts   CRUD em `peopleflow_movimentacoes` (exclusiva deste portal)
    cargosCustomRepository.ts    CRUD em `peopleflow_cargos_custom` (exclusiva deste portal)
    desligadosRepository.ts       CRUD em `peopleflow_desligamentos` (rescisão/GRRF, exclusiva deste portal)
    acessosRepository.ts          chama as Serverless Functions em api/*.ts (nunca fala com o Supabase
                                 Auth admin direto do navegador)
    portalRepository.ts          catálogos estáticos (tipos, perfis) — sem backend
  domain/                     regras de negócio puras, sem React (testáveis isoladamente):
    hierarquia.ts              e-mail/perfil por colaborador, hierarquia de gestores, aprovador por papel
                              (buildAccess já exclui colaborador desligado)
    permissoes.ts              o que cada perfil pode ver/fazer
    workflow.ts                motor de aprovação: gera etapas, aprova/reprova, gera próximo ID
    formMovimentacao.ts        valida e monta uma Movimentacao a partir do formulário "Nova movimentação"
    agregados.ts                agregações derivadas (headcount por depto, cargos, contagem por gestor)
    desligados.ts                filtra colaboradores desligados e calcula pendência de fechamento financeiro
    historico.ts                 reconstrói a trilha de eventos (criação + etapas) de uma lista de
                              movimentações — usado por Histórico e pelo detalhe de Desligados
    colors.ts / avatar.ts / documentos.ts / dates.ts   utilitários de apresentação
  store/                      estado da aplicação via useReducer + Context (`PortalStoreContext`);
                              carrega colaboradores/movimentações/cargos/desligamentos financeiros do
                              Supabase assim que há sessão autenticada e zera tudo ao deslogar.
                              `useConta()` cruza o e-mail autenticado com os colaboradores para achar a
                              Conta (nome/cargo/perfil). `usePortalData()` combina Conta + store e expõe
                              dados já filtrados por perfil + as ações de workflow (que gravam no Supabase
                              antes de atualizar o estado local) — é o principal hook consumido pelas páginas
  auth/                       AuthContext (Supabase Auth, magic link) + guarda de rotas (RequireAuth)
  components/
    ui/                        biblioteca de componentes visuais (Badge, Card, Button, Modal, Drawer, ...)
    layout/                    Sidebar, Header, AppShell (com navegação sensível a perfil)
    shared/                    ToastContext, NovaMovimentacaoModal (reusado por Dashboard e Workflow)
  features/                   uma pasta por página (dashboard, colaboradores, departamentos, cargos,
                              tipos, workflow, aprovadas, historico, desligados, acessos, auth), cada
                              uma com seu .tsx + .module.css
```

Estilo: CSS Modules (sem framework de UI), tokens de design (cores, raios, sombras) como variáveis CSS em `src/index.css`, fonte Montserrat. Roteamento com React Router v7, ícones via `lucide-react`.

## Banco de dados compartilhado com o Portal SST

Os dois portais MSB usam o **mesmo projeto Supabase**, mas cada um só lê/escreve o que é seu:

| Tabela | Dono | Quem lê | Quem escreve |
|---|---|---|---|
| `colaboradores` | Portal SST | SST (tudo) e PeopleFlow (nome/cargo/departamento/vinculo/depto_code/nivel/gestor/admissao/desligado/data_desligamento/motivo_desligamento/desligado_by) | Cadastro base: criado como pré-cadastro pelo PeopleFlow ao concluir uma Admissão (`api/criar-pre-cadastro.ts`), completado (cpf/nascimento) pelo SST na tela Editar colaborador. `cargo`/`departamento`/`gestor` também atualizados pelo PeopleFlow ao concluir Promoção/Transferência (`api/atualizar-cargo-departamento.ts`). `desligado`/`data_desligamento`/`motivo_desligamento`/`desligado_by`: só o SST grava (botão "Desligar colaborador" dele) — o PeopleFlow nunca grava esses campos diretamente, só sinaliza via `peopleflow_desligamento_pendente` abaixo. `admissao` também editável manualmente pelo RH via `api/atualizar-admissao.ts`. Fora essas exceções pontuais (todas RH-only, via service role), PeopleFlow só lê `colaboradores` |
| `peopleflow_desligamento_pendente` | Portal PeopleFlow | Os dois — PeopleFlow escreve, SST lê e apaga | PeopleFlow cria/atualiza a linha ao concluir uma movimentação de Desligamento (direto do navegador). SST lê para mostrar "Desligamento pendente" no Dashboard dele e apaga a linha ao confirmar o desligamento de verdade (tela "Desligar colaborador") |
| `peopleflow_movimentacoes` | Portal PeopleFlow | Só PeopleFlow | Só PeopleFlow (direto do navegador, usuário autenticado) |
| `peopleflow_cargos_custom` | Portal PeopleFlow | Só PeopleFlow | Só PeopleFlow (direto do navegador, usuário autenticado) |
| `peopleflow_desligamentos` | Portal PeopleFlow | Só PeopleFlow | Só PeopleFlow (direto do navegador, usuário autenticado) — valor da rescisão e da GRRF, editados na tela `/desligados` |
| `peopleflow_descricoes_cargo` | Portal PeopleFlow | Só PeopleFlow | Só PeopleFlow (direto do navegador) — escrita liberada por RLS a qualquer autenticado, mas a UI só mostra o botão de editar para perfil RH |
| `peopleflow_descricoes_cargo_historico` | Portal PeopleFlow | Só PeopleFlow | Só PeopleFlow — log append-only, uma linha por campo editado em `peopleflow_descricoes_cargo` |

Isso significa: **qualquer pessoa cadastrada no SST também aparece automaticamente no PeopleFlow** (mesmo nome/cargo/departamento), mas só consegue **entrar** no PeopleFlow se tiver uma conta Supabase Auth provisionada (passo 2 acima) — ter conta no SST não dá acesso automático ao PeopleFlow, e vice-versa.
